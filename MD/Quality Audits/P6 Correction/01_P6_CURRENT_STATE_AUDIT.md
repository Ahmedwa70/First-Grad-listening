# 01 — P6 Current State Audit

**التاريخ:** 14 أغسطس 2026  
**النوع:** تحليل وتوثيق فقط — لا تعديلات برمجية  
**النطاق:** P6 الحالي (`initP6`, `renderP6`, `advanceP6`, `p6AnswerVisible`, `discriminationRounds`) وعلاقته بعقد Activity Engine  
**خارج النطاق:** تعديل `app.js` أو`lesson-01.js` أو`css/style.css` أو`lecture-01.html` أوActivity Engine أوأي Renderer حالي.

---

## 1. سياق القرار ونطاقه

يعمل الدرس الحالي كنظام صفّي يقوده المعلم، مع بيانات درس مجمدة في `lesson-01.js`، وحالة مركزية وrenderers مرتبطة بالمراحل في `app.js`. تصف بنية المشروع P6 الحالي بوصفه «التمييز السمعي» بثلاث جولات: D1 للتعرف على الصوت، وD2 للمقارنة بين صوتين، وD3 للأصوات المتقاربة [1] [2].

تؤكد وثائق Activity Engine أن النشاط يجب أن يكون مستقلاً عن اسم المرحلة والـDOM وبيانات درس بعينها، وأن المرحلة يجب أن تختار النشاط عبر configuration فقط [3] [4]. لذلك لا يهدف هذا التدقيق إلى استبدال P6 أو الحكم على CSS، بل إلى تحديد ما يمكن الحفاظ عليه وما يجب فصله قبل أي Migration.

> **قاعدة هذا التدقيق:** المحافظة على سلوك النسخة الحالية، ثم فصل النشاط القابل لإعادة الاستخدام تدريجياً؛ لا Rewrite ولا إعادة تسمية سطحية.

## 2. ملخص الحالة الحالية

| المجال | الحالة الحالية | الحكم |
|---|---|---|
| اسم المرحلة | `P6 — التمييز السمعي` | صحيح كتسمية تجربة حالية، لكنه لا يكفي كحد معماري للنشاط |
| البيانات | `LESSON_01.discriminationRounds` بثلاث جولات | فصل بيانات جيد جزئياً، لكن schema مخصص للـrenderer الحالي |
| الحالة | مفاتيح `p6RoundIndex`, `p6PairIndex`, `p6AnswerVisible`, `p6RevealStep`, `p6SoundPlayed` داخل `STATE` | مركزية لكنها مرتبطة صراحةً بـP6 |
| التحكم | Space/زر كشف/أزرار جولة/أزرار صوت | قابل للتشغيل في الفصل، لكنه لا يمر عبر Teacher Command Bus موحد |
| الصوت | `p6PlaySound()` يستدعي `p3PlaySound()` ثم AudioManager | إعادة استخدام جيدة لمسار الصوت المحلي والـfallback |
| العرض | `renderP6()` يبني markup عبر template strings وhandlers inline | اقتران قوي بين التعريف والحالة والـDOM |
| التراجع | منطق خاص داخل `retreat()` | يعمل جزئياً، لكنه ليس Undo مبنياً على contract أوsnapshot |
| التقويم | كشف إجابة بعد الاستجابة الجماعية | ملاحظة صفية غير مسجلة؛ لا يوجد حدث/سجل أداء منظم |

## 3. التحليل التربوي

### 3.1 ما الهدف الحالي فعلياً؟

الهدف المنفذ هو تدريب صفّي موجه على الاستماع قبل كشف الإجابة. يبدأ D1 بصوت حرف ويطلب رفع عدد الأصابع الموافق، ثم يقارن D2 صوتين عبر «نفس أم مختلف؟»، ويعرض D3 مجموعة أصوات متقاربة مع ملاحظة تفسيرية. هذا ينسجم مع مبدأ **الصوت أولاً** والاستجابة الحسية المتعددة [5].

المسار الفعلي هو:

```text
صوت → استجابة جسدية جماعية → كشف بصري → تفسير مختصر
```

وهذا مسار صحيح **للتدريب السمعي الموجه**، خصوصاً للطالب الصيني A0 الذي يحتاج إلى تكرار منظم وبيئة لا تعاقب الخطأ علناً. لكن المسار لا يصل إلى إنتاج مستقل؛ لا توجد كتابة، ولا جملة شفوية فردية، ولا ملاحظة منظمة للمعلم حول من يحتاج دعماً. لذلك لا يصح وصف P6 الحالي بأنه يحقق وحده المسار الأشمل:

```text
صوت → تمييز → إنتاج مستقل
```

### 3.2 هل يخدم الطالب الصيني المبتدئ؟

**نعم، جزئياً.** قوة النشاط أنه لا يبدأ بطلب قراءة أو كتابة، ويستخدم إشارة جسدية منخفضة المخاطر مثل الأصابع/الإبهام. كما أن حروف ب/ت/ث/ن مناسبة للمقارنة؛ فهي تشترك في بنية بصرية مع اختلاف النقاط، ويستفيد الطالب من التكرار والمقارنة [5].

لكن التصميم الحالي يحتاج قبل التنفيذ المستقبلي إلى ثلاثة ضوابط تربوية واضحة:

1. مثال واحد محلول قبل السؤال الأول في كل نوع نشاط.
2. فصل لحظة الاختبار السمعي عن ظهور الحرف/الفونيم في D3 حتى لا يحل الشكل محل الاستماع.
3. مرحلة لاحقة تحول الاستجابة الجماعية الآمنة إلى كتابة أو إنتاج شفهي فردي مدعوم.

### 3.3 هل يبدأ بالاستماع قبل الشكل؟

في D1 وD2، نعم: زر الصوت يسبق كشف الإجابة، ولا يظهر الحرف الصحيح حتى أمر الكشف. هذه خاصية يجب الحفاظ عليها. في D3، تظهر الحروف والفونيمات كأزرار تشغيل، لذلك يكون الفصل بين الصوت والشكل أضعف. هذا مقبول للمراجعة التفسيرية بعد التعرف، لكنه ليس الاختيار الصحيح إذا كان الهدف اختبار التمييز السمعي الخالص.

### 3.4 علاقة P6 الحالي بالـBlueprint المعتمد

تصف خريطة التنفيذ والـInstructional Blueprint المتأخر في الدرس P6 بوصفه توطيداً وتقويماً يتضمن Rapid Retrieval ثم Silent Dictation ثم Exit Sentence، بينما النسخة الحالية تبقي P6 كتمييز سمعي يدوي [6] [7]. كما تسجل حالة المشروع قراراً سابقاً يقضي بالإبقاء على التمييز السمعي وتأجيل الإملاء/الخروج/الواجب [2].

هذا **ليس سبباً للـRewrite**. القرار الصحيح هو توثيق الفرق: التمييز السمعي نشاط له قيمة ويجب حفظه كمكوّن مستقل؛ أما P6 الجديد فيمكن أن ينظمه مع أنشطة التوطيد والإنتاج عندما يُعتمد نطاق التنفيذ رسمياً.

## 4. التحليل التقني

### 4.1 `initP6`

`initP6()` يعيد تهيئة مفاتيح P6 داخل `STATE`، يحقن حاوية `.p6-container` في `#content-zone`، يستدعي `renderP6()`، يحدث شريط المرحلة، ثم يبدأ `PhaseTimer`.

| نقطة قوة | المشكلة المعمارية | ما يجب الحفاظ عليه |
|---|---|---|
| إعادة تهيئة واضحة عند دخول المرحلة | تهيئة النشاط مربوطة مباشرةً بـP6 وبعنصر DOM محدد | مفهوم reset الكامل عند الدخول |
| استخدام `PhaseTimer` و`updatePhaseBar` المشتركين | لا توجد Activity Instance مستقلة | تكامل shell مع المعلم والمؤقت |
| نقطة دخول واحدة | إنشاء DOM جزء من init المنطقي | فصل init lifecycle عن mount/render لاحقاً |

### 4.2 `renderP6`

`renderP6()` يختار الجولة والعنصر الحالي، ثم يبني header، وteacher guide، وعداد التقدم، وأزرار الصوت، ومنطقة الإجابة، وأزرار الكشف/التالي. يضمّن داخل renderer قواعد تختلف حسب `identify`, `sameordiff`, و`close`.

| نقطة قوة | الاقتران الحالي | أثره |
|---|---|---|
| ترتيب بصري واضح: صوت ثم سؤال ثم كشف | renderer يعرف نوع النشاط وقواعده التربوية | يصعب استخدام D2 خارج P6 دون نسخ renderer |
| progressive reveal في D1 | عدد خطوات الكشف hard-coded داخل renderer | لا يمكن تعريف reveal contract مستقل لكل Activity |
| `P6_GUIDES` يوضح خطوة المعلم | التلميح يعتمد على round type والحالة الداخلية | لا يمكن توحيده مع Teacher Controller |
| DOM-stable reveal في `p6ApplyReveal()` | يعتمد على selectors وclasses P6 الخاصة | قابل للاحتفاظ كـRenderer Adapter لا كمنطق Core |
| أزرار صوت كبيرة وحالة تشغيل مرئية | handlers inline مرتبطة بالدوال العالمية | يصعب الاختبار دون DOM |

### 4.3 `advanceP6`

`advanceP6()` يدمج ثلاثة أدوار: كشف الإجابة، التقدم داخل كشف D1 متعدد المراحل، التقدم بين عناصر الجولة، والانتقال بين الجولات ثم بين المراحل. هذا يعمل حالياً، لكنه يجعل transition rules داخل دالة P6 بدلاً من contract مستقل.

المطلوب مستقبلاً ليس حذف الدالة مباشرة، بل نقل القواعد بالتدرج إلى Activities:

- `REVEAL` يغير حالة النشاط فقط.
- `NEXT` ينتقل إلى عنصر تالٍ أو يُكمل Activity وفق completion condition.
- `BACK/UNDO` يعيد snapshot مسموحاً دون تشغيل صوت تلقائي.
- يحدد lesson flow متى ينتقل من Activity إلى أخرى، لا `advanceP6()` وحدها.

### 4.4 `p6AnswerVisible` و`p6RevealStep`

هذان المفتاحان يقدمان فائدة حقيقية: يمنعان كشف الإجابة قبل سماع الصوت ويدعمان الكشف المتدرج. المشكلة ليست في وجودهما، بل في أن معناهما مرتبطان بـP6 وبتفاصيل D1. في Activity Contract يجب أن يتحولا إلى مفهوم عام:

```text
state.phase = response | reveal | completed
reveal.level = 0..n
```

بهذا يحتفظ renderer بأسلوب الكشف الحالي، لكن يصبح عدد المستويات وسلوكها جزءاً من تعريف النشاط لا من `if (round.type === 'identify')`.

### 4.5 `discriminationRounds`

البيانات الحالية صالحة كبذرة محتوى، لا كتعريف نشاط. تحتفظ بترتيب الجولات، و`playId` أو`playIds` أو`ids`، والإجابة/الملاحظة. هذا جيد لأنه منفصل عن CSS وHTML. لكنها تستخدم ثلاثة أشكال مختلفة للبيانات داخل مجموعة واحدة، ما يجبر `renderP6()` على معرفة أنواع متعددة.

القرار المقترح:

| يبقى في Lesson Data | ينتقل إلى Activity Definition | يبقى في Renderer |
|---|---|---|
| الحروف المستهدفة، ترتيب العناصر، مراجع الصوت، الإجابات، الملاحظات التعليمية | حالات النشاط، الأوامر، validation، success/completion criteria، event types | تخطيط البروجكتور، الأزرار، الحركة، الألوان، DOM selectors |
| أي نص خاص بالدرس أو كلمة/حرف | لا يحتوي lesson ID أو P6 | لا يقرر هدفاً تربوياً أو انتقالاً |

## 5. نقاط القوة التي يجب الحفاظ عليها

1. **Audio First:** لا تكشف D1/D2 الإجابة قبل الاستماع.
2. **Teacher Controlled:** المعلم يقرر التشغيل والكشف والانتقال.
3. **استجابة حسية منخفضة القلق:** الأصابع والإبهام مناسبة للصف الكامل.
4. **AudioManager المشترك:** MP3 محلي مع fallback، ولا يجب تجاوزه.
5. **Progressive Reveal:** كشف D1 المتدرج مفيد كتغذية راجعة وتعزيز.
6. **Teacher Guidance:** نص الخطوة الموجه للمعلم فكرة قابلة للتعميم.
7. **Projector-friendly visual hierarchy:** زر الصوت والمساحة المركزية مناسبان كنقطة بداية للـrenderer القادم.
8. **تراجع جزئي:** السلوك الحالي يثبت أهمية back/reveal reversal حتى لو لم يكن contract-based بعد.

| حرجة | لا توجد بيانات أداء/أحداث منظمة | الكشف يحدث بصرياً فقط | Read-only event bridge قبل أي renderer جديد |

| عالية | الانتقال إلى المرحلة التالية جزء من `advanceP6` | lesson flow داخل logic نشاط | نقل orchestration إلى lesson activity map لاحقاً |
| متوسطة | D3 يعرض الشكل أثناء المقارنة | اختبار السمع يتداخل مع دعم بصري | جعله Review أو إخفاء الشكل قبل الاستجابة |
| متوسطة | التراجع غير موحد | منطق P6 خاص ومحدود | اعتماد Undo contract مع سياسة لا تعيد الصوت تلقائياً |
| متوسطة | Teacher controls ليست command vocabulary موحداً | handler/state خاصان بالمرحلة | ربط الاختصارات بأوامر عامة لاحقاً |
| متوسطة | التقويم الجماعي غير مرئي للـanalytics | لا يوجد `needs-review` أو observation event | تسجيل ملاحظات المعلم محلياً فقط |

## 7. القرار المعماري

P6 لا يحتاج UI-only fix، ولا يحتاج Rewrite. يحتاج **Migration تدريجياً على مستوى Activity**.

القرار يتكون من ثلاث طبقات:

1. **الحفاظ المؤقت:** تبقى `initP6`, `renderP6`, `advanceP6` والـCSS الحالية كما هي حتى يثبت البديل.
2. **Read-only Bridge:** يراقب P6 الحالي ويحوله إلى أحداث/محتوى لعقود مستقلة من دون تغيير العرض.
3. **ترحيل Activity واحدة:** يبدأ بـ`same-or-different.v1` لأنه أصغر عقداً، مع fallback للـrenderer القديم، ثم تُرحّل بقية الأنشطة.

> **قرار عدم التنفيذ:** لا يُنقل P6 الحالي مباشرة إلى Vue أوTypeScript، ولا يُستبدل renderer قبل أن تصبح transition rules وevent log وTeacher commands قابلة للتحقق.

## 8. جاهزية الانتقال

| السؤال | الحكم |
|---|---|
| هل P6 صالح للاستعمال الحالي؟ | نعم، كلوحة تدريب سمعي يقودها المعلم |
| هل هو Activity Engine-ready مباشرة؟ | لا؛ يحتاج content adapter وbridge |
| هل يجب إعادة كتابة P6؟ | لا |
| هل يجب تعديل UI فقط؟ | لا |
| هل الترحيل التدريجي مناسب؟ | نعم، وهو المسار المعتمد |
| ما أول خطوة تنفيذية مستقبلية؟ | Read-only Bridge بلا تغيير مرئي |
