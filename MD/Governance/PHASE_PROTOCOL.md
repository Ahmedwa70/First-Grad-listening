# PHASE_PROTOCOL.md — البروتوكول الرسمي الإجباري لأي Phase

> هذا الملف هو **القالب الرسمي الإجباري** لأي Phase مستقبلية على هذا المشروع.
> لا يُنفَّذ أي Phase تطويرية على `Lesson-01-classroom-P6-Fixed` دون تعبئة هذا القالب أولاً
> وإنشاء تقرير `Phase-X-Report.md` بعد التنفيذ.
> المرجعية: `AI_WORKFLOW_RULES.md` + `SOURCE_OF_TRUTH.md` + `ARCHITECTURE_RULES.md`.

---

## Phase Protocol

### 1. Phase Identity

| الحقل | القيمة |
|---|---|
| Phase Name | (اسم المرحلة) |
| Phase Number | (الرقم التسلسلي) |
| Related Module | (الوحدة المتأثرة: P1–P7 / CSS / الصوت / غير ذلك) |
| Date | (التاريخ) |

---

### 2. Context Before Work

يجب تحديد كل مما يلي **قبل** أي تنفيذ:

- **الحالة الحالية**: ما هو موجود ويعمل الآن (من `CURRENT_STATE.md`).
- **المشكلة الموجودة**: الوصف الدقيق للخلل أو النقص المراد معالجته.
- **سبب الحاجة للتعديل**: لماذا يلزم هذا التغيير الآن (وما الدليل/المصدر).
- **الملفات المرجعية التي تمت قراءتها**: قائمة فعلية بالملفات/الوثائق المقروءة
  (Work plan، الكود، التقارير) مع أي ملاحظات.

---

### 3. Required Memory Reading

قبل أي تنفيذ يجب قراءة الملفات التالية بالترتيب (إلزامية):

1. `ACTIVE_TASK.md`
2. `CURRENT_STATE.md`
3. `DESIGN_PHILOSOPHY.md`
4. `ARCHITECTURE_RULES.md`
5. `SOURCE_OF_TRUTH.md`

ثم الملفات الخاصة بالمهمة (Work plan، الكود المتأثر، تقارير Phase سابقة).

---

### 4. Goal Definition

- **الهدف الرئيسي**: بيان واحد واضح لما تحققه هذه المرحلة.
- **ما الذي سيتم تحسينه**: قائمة دقيقة بالعناصر المستهدفة.
- **ما الذي لن يتم تغييره**: قائمة صريحة بالعناصر الخارجة عن النطاق (للحماية من التعديل الزائد).

---

### 5. Allowed Scope

مثال (يُعدَّل حسب طبيعة المرحلة):

```
Allowed:
- css/style.css
- app.js
- documentation

Forbidden:
- lesson-01.js
- data
- AudioManager
- navigation logic
```

> القاعدة: أي عنصر غير مذكور في `Allowed` يُعتبر **ممنوعاً** افتراضياً.

---

### 6. Design Validation

أي تعديل **بصري** يجب تقييمه مقابل كل من:

- [ ] **Projector-first** — واضح من مسافة بعيدة، أحجام خطوط كبيرة، تباين عالٍ.
- [ ] **Teacher-controlled** — لا يعتمد على تفاعل الطالب المباشر؛ يظل المعلم هو المحرك.
- [ ] **RTL** — اتجاه سليم، تخطيط يعمل مع اللغة العربية.
- [ ] **Progressive Reveal** — لا يُعرض كل شيء دفعة واحدة؛ كشف تدريجي.
- [ ] **Classroom readability** — مقروء ضمن ضجيج/إضاءة الفصل على شاشة كبيرة.

---

### 7. Technical Validation

قبل اعتماد أي Phase يجب التحقق من:

- [ ] عدم كسر لوحة المفاتيح (Space/←/Backspace/A/F/1-7).
- [ ] عدم كسر الصوت (كل تشغيل عبر `AudioManager`).
- [ ] عدم كسر التنقل بين المراحل (`advance`/`retreat`/`goToPhase`).
- [ ] عدم تغيير البيانات (`lesson-01.js` مجمّد — لا يُمس).
- [ ] عدم وجود Scroll (المحتوى كامل على شاشة واحدة لكل خطوة).

اختبارات القياس (إجبارية):

| القياس | النتيجة |
|---|---|
| 1280×720 | (مناسب / مشكلة) |
| 1366×768 | (مناسب / مشكلة) |
| 1920×1080 | (مناسب / مشكلة) |

---

### 8. Phase Report Requirement

بعد التنفيذ **يجب** إنشاء `Phase-X-Report.md` (في مجلد المشروع أو حسب الاتفاق) ويحتوي:

- الهدف (من القالب).
- الملفات المعدلة.
- التغييرات المنفذة.
- ما لم يتغير.
- الاختبارات المنفذة (من القسم 7).
- المشاكل المتبقية / ما يحتاج متابعة.

ثم يُحدَّث: `CHANGELOG.md` + `CURRENT_STATE.md` + `ACTIVE_TASK.md`.

---

## تذكير إلزامي

- لا تنفذ Phase دون طلب صريح من المستخدم.
- لا تعدّل ملفات المشروع التعليمية في أي مهمة توثيقية/تنظيمية.
- عند أي تعارض: راجع `SOURCE_OF_TRUTH.md` ثم `AI_WORKFLOW_RULES.md` ثم اسأل المستخدم.
